## 背景

之前上学的时候，赶上腾讯云做活动，入手了一个三年两百多 rmb 的轻量应用服务器，拿来当跳板机，以及部署一些非常轻量的东西。

然而最近这台服务器快要到期了，于是我又从华为云捡了一个一年 38rmb 的小鸡来接着用。

在配环境的过程中，我发现自己做了很多事情，比如给防火墙开端口、比如创建用户（这台小鸡还有我的一个高中同学在使用）、比如装一些常用的工具和依赖。未来可能还需要配监控、配 WireGuard 内网等等。

然而作为一名程序员，我天生地讨厌的重复的、没有自动化的工作。

那很符合直觉的想法就是，我搞一套 Inrastructure as Code(IaC) 的工具，然后用类似 GitOps 的方式来管理。

## 一些直觉

我在此之前完全没有自己配置过 Inrastructure as Code ，上班的时候虽然改过一些 Terraform 的代码，但是只知道 MR 合进去了，主分支流水线跑完了，改动就 Magically 生效了，根本不知道其中的原理。

不过至少通过观察现象，还是能总结（臆测）出一些 Infrastructure as Code 的特质，比如：

### 描述最终状态，而不是操作步骤

这个其实挺显然的，因为我们完全不感知被操作对象的当前状态，自然也不可能直接写出操作步骤。

有点类似 Docker Compose YAML 或者 Kubernetes 的配置文件，都是声明式的。

我们只描述我们期望的最终状态，如果这个对象不存在，就自动地创建；如果这个对象当前状态和期望状态不符，工具（比如 kubelet）就会自动分析当前状态和目标状态，生成一个操作序列，然后执行。

### 简单方便地回滚

这个应该是结合版本管理来实现。我们只需要 Revert 新的更改，就能回到旧的状态。

- SaltStack

DeepSeek 还提到了 NixOS ，就我对 NixOS 的粗浅了解来说，感觉它确实是 IaC 的终极形态了。但是这对于我来说还是太超前了，先老老实实用 Debian 吧。

翻了下对应的 GitHub 项目，发现按 Star 顺序排序是 Ansible 的 Star 最多，SaltStack 其次，最后是 Puppet 。

由于我完全不懂 IaC ，所以多读一读文档肯定对于我培养这方面的 Common Sense 有帮助，所以我准备把这三个产品的文档都先读一读。

我猜 Star 多的项目用的人应该也更多，文档应该也要更好，所以我准备按照 Star 升序来读文档。
